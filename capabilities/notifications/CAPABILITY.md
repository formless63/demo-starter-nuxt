# Notifications

Private `@repo/nuxt-notifications` provides durable in-app notification records and optional external delivery. Hard dependency: **Jobs**, enforced by catalog, package peer and Nuxt moduleDependencies. PostgreSQL/Drizzle are baseline requirements; authentication is application-owned. Email, Realtime, Audit and Observability are optional integrations with no package dependencies. ntfy is optional. Clean consumers explicitly install/enable; the reference application enables it. Evaluation: [NOTIFICATIONS_MODULE_EVALUATION.md](../../NOTIFICATIONS_MODULE_EVALUATION.md).

## Install and schema

Enable `'@repo/nuxt-jobs'` and `'@repo/nuxt-notifications'`. Import runtime helpers from `@repo/nuxt-notifications/server`, and include `notification` from **`@repo/nuxt-notifications/schema`** in the application's Drizzle schema. The separate schema entry works with Drizzle Kit's schema loader without importing Jobs runtime. Applications generate, review and commit SQL, apply application migrations plus `jobs:migrate` explicitly, and never auto-migrate at startup. Package/module creates no routes, clients, schema or external connections on build/start.

Table `notification`: generated UUID id; recipientId ≤128; namespaced lowercase type ≤128; plain title ≤200; plain body ≤4096 UTF-8 bytes; bounded JSONB metadata default `{}`; generated createdAt timestamptz(3); nullable readAt timestamptz(3). Create ignores caller overrides of id/createdAt/readAt. No HTML rendering/body API, recipient FK cascade or capability-owned retention daemon. Titles/identifiers must be well-formed and control-free; plain bodies permit ordinary tabs/newlines/carriage returns and reject other control characters. Create and supplied list type filters use the identical strict lowercase dot-separated event grammar; undefined omits the filter, while empty, unqualified and empty-segment values are invalid. Titles are nonempty and not whitespace-only, measured by JavaScript string length (≤200), and preserved exactly, including markup-looking `<tag>` text. Consumers render them as escaped text.

Three B-tree indexes: `(recipient_id, created_at DESC, id DESC)`, `(recipient_id, read_at, created_at DESC, id DESC)`, `(recipient_id, type, created_at DESC, id DESC)`.

Metadata root is a plain object, ≤8192 UTF-8 bytes, depth≤6 (root0), 50 keys/object, 100 array items, 1024 nodes, nonempty key≤64 and string≤1024. Reject runtime/non-JSON values, accessors, cycles, prototype pollution, sparse/custom arrays, controls/malformed Unicode. Keys are preserved exactly, including whitespace-only keys; normalization is used only for sensitive-key screening, rejecting password/passwd/pwd/secret/token/authorization/cookie/apikey/credential substrings and request/session/body/header/headers containers. Nothing rejected is echoed in errors.

## Server operations and ownership

`appendNotification(txOrDb, input)` accepts a supplied database or existing transaction executor. `queryNotifications(db, recipientId, { unreadOnly, type, pageSize, cursor })` always predicates on the server-supplied recipient. Default page25, range1–100, order createdAt DESC/id DESC, keyset cursor canonical base64url of `[1, createdAtISO, id]`, no OFFSET. Cursor is pagination state, never authorization.

`markRead(db, recipientId, id)` and `markUnread` put recipient ownership inside the SQL update. Both are idempotent and return whether an owned row exists after the requested state; foreign and missing IDs both return false. Read preserves the existing read timestamp on repeated calls. `getNotification(db,id)` is a **worker/server primitive without recipient policy**, not a browser route helper; application routes must use the recipient-scoped query/update APIs.

Applications can atomically mutate domain data, append a notification and use Jobs `sendRegisteredJobInTransaction` / Nitro `sendJobInTransaction` with the same transaction. Root `createApplicationNotification` demonstrates append/enqueue commit then optional hint; the packed fixture proves domain mutation, insert and enqueue rollback together.

## Delivery and adapters

Compose `createNotificationJobs({ load, adapters })` into the application's existing shared Jobs registry/worker. Job `notifications.deliver` payload is **only `{ notificationId, channel }`**, channel email/ntfy. Recipient/content/topic/token/address/config never enters Jobs data. Each attempt reloads the durable record and resolves the current target. Policy: 5 retries after initial, 30-second delay, exponential backoff/jitter, max delay900, expiry60 seconds, pending/completed retention1 day. Safe transient failures throw retryable NotificationError; permanent failures return terminal rejected output because Jobs retries thrown errors. Missing record/disabled adapter returns terminal rejected. No exactly-once claim; ambiguous external acceptance can duplicate delivery, and applications own their policy.

Core has no Email dependency or SMTP implementation. `server/notifications/email-adapter.ts` maps stable recipient ID to current email then calls the existing Email capability once using plain text. Accepted delivers; partial/rejected and ambiguous/non-retryable failures settle rejected; only typed EmailError with retryable=true and code connection (proven pre-send failure) or temporary-rejection retries. Timeout/reset/unknown acceptance, unknown exceptions and partial outcomes stay terminal; cancellation/deadline after SMTP invocation stays terminal. Worker and Nitro share the registry. No automatic Audit copying of title/body/metadata; Audit remains optional.

`createNtfyAdapter(resolveTopic)` owns provider-neutral official HTTP JSON publishing. Server-only `NTFY_BASE_URL` is required on use; **no public ntfy.sh default**. HTTPS normally; HTTP only literal localhost, 127.0.0.1 or [::1] with explicit NODE_ENV=development/test (alternate IP spellings rejected), no URL credentials/query/fragment, app-selected trusted server root. `NTFY_TOKEN` is an optional Bearer secret. `NTFY_TIMEOUT_SECONDS` defaults10, integer1–30. Current recipient-to-topic lookup occurs during execution, never queued; root intentionally supplies no guessed topic policy. Configure/extend that application resolver to use ntfy.

The adapter POSTs `{ topic, title, message }` to the configured ntfy server root using native Node24 fetch, manual redirects and a bounded attempt (target lookup included). It discards/cancels the response body without reading/logging it. Network/timeout/408/425/429/5xx are transient; redirects/other4xx are permanent. It never creates/deletes remote topics/resources. Compatibility tests use disposable local **ntfy2.28.0**, never a public service.

## Realtime, routes and privacy

Root session-authenticated `/api/notifications` lists only the current user; `/api/notifications/:id/read` marks owned rows; `/api/notifications/demo` creates only the current user's demonstration notification and optionally enqueues finite delivery channels. No address/topic/config in browser producers. Packages force no consumer routes.

After the transaction promise commits, root optionally publishes `notifications.created` with **only `{ notificationId }`**. Failed realtime leaves durable records/Jobs committed; clients fetch authoritative notifications. No hint before commit or on rollback. Optional telemetry uses operation, finite channel/outcome, duration, retry count; never recipient/email/title/body/metadata/topic/token. Safe NotificationError codes contain no raw cause, backend URL or provider response.

## Verification and removal

`bun run packages:test notifications` exercises actual application migrations/indexes, domain/notification/Jobs commit/rollback and minimal payload, recipient isolation/read/unread, filters/cursor, actual Jobs retry/permanent policy, local ntfy protocol, backendless boot and packed removal retaining Jobs. Root tests cover metadata bounds, HTTP status policy, Email uncertainty and post-commit hints. Generic runtime/post-removal/cleanup hooks keep the disposable database through final rebuild and verify rows, indexes, migration history and retained Jobs before teardown.

Stop producers and drain/stop delivery work first. Remove module/dependency, application routes, delivery definitions/registry imports, wrappers and optional hints; update worker lifecycle cleanup. Preserve the notification table, existing rows and **applied migration files/history**. To stop using the package schema, replace its import with an application-owned equivalent if future Drizzle generation still includes this table; never generate a DROP merely because code was pruned. Retain Jobs and independently selected Email/Realtime/Audit/Observability. Never alter remote ntfy resources during removal.

Delivery preparation checks the native Jobs cancellation signal before loading and races record/current-target resolution, handling late rejection without late SMTP. A composed 50-second safety deadline settles terminally before the 60-second Jobs expiry. Once SMTP begins, cancellation cannot undo acceptance; the underlying operation may finish after the wrapper returns rejected, with no retry from that terminal result. Unknown adapter failures are terminal; only explicit safe typed transient errors retry. Pre-delivery application loading retries only known connection/serialization failures. External delivery remains subject to worker crash/claim loss and cannot promise exactly once. ntfy network/deadline retry can duplicate an accepted publication. Jobs output contains only allowlisted outcome/code, never provider extras.

The generic Notifications lifecycle retains its disposable database through packed removal and final rebuild, then compares notification rows/indexes/applied migration history and Jobs schema before cleanup in finally. Root check and ordinary production verification also run actual disposable Mailpit compatibility.
